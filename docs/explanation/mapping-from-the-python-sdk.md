# Mapping from the Python SDK

If you already know `typesafe-sdk` in Python, most of the Go SDK's shape will look familiar in outline and unfamiliar in detail. Both SDKs wrap the same System One API and preserve the same wire semantics, but Go's type system, concurrency model, and error-handling idioms push several Python conveniences into different forms. This page walks through why each translation looks the way it does, rather than just listing it.

## One client, not two

Python exposes `TypeSafeClient` and `AsyncTypeSafeClient` because an `async def` function cannot be called from ordinary code without an event loop, so the SDK ships two client classes with parallel methods. Go has no such split. `NewClient` produces a single `*Client`, and both `SystemOne` and `ListModels` take a `context.Context` as their first argument. Combined with goroutines, `ctx` already gives a Go caller everything the async client exists to provide in Python: cancellation, deadlines, and the ability to run many calls concurrently without blocking a program on any one of them. A second, "async" client type would just be the same struct wrapped in more goroutines the caller was always free to start — so the design leaves it out rather than ship a redundant type.

## Typed decoding without a validation runtime

Python's `response_model=` parameter hands `system_one` a pydantic model and gets back a validated instance, because pydantic can inspect arbitrary Python objects against a schema at runtime. Go's `encoding/json` has no equivalent introspection step: it decodes into whatever concrete type you give it, full stop. `SystemOneAs[T any](ctx, c, state, questions, opts...) (T, *SystemOneResponse, error)` reproduces the *convenience* of `response_model=` — decode answers straight into your own struct — without reproducing the mechanism. `T` is a plain struct whose fields are `NoulAnswer`, `ChoiceAnswer`, or `ScoreAnswer` with `json` tags naming the question keys, and the `answers` object is unmarshaled directly into it. The validation pydantic would do centrally instead lives on the answer types themselves: each implements `json.Unmarshaler`, so decoding an answer also checks that its `type` discriminator matches what the field expects. The correctness guarantee ends up in the same place either way — a caller gets an error if the shape doesn't match — but it's distributed across small `UnmarshalJSON` methods instead of concentrated in one schema validator.

## One error struct instead of an exception hierarchy

Python's exception hierarchy lets a `try`/`except` block catch by class. Go doesn't privilege type switches the same way, and a status-specific type for every one of a dozen HTTP status codes would mean a dozen types to track. So the Go SDK collapses that hierarchy into one `APIError` struct carrying `Status int`, and callers branch on the status directly, or use `IsAuthError`, `IsRateLimited`, or `IsRetryable` when the check is common enough to name. `RateLimitError` is the one exception: because a 429 carries a `RetryAfter` value nothing else does, it gets its own type, `RateLimitError{APIError; RetryAfter time.Duration}`, that still unwraps to `*APIError` via `errors.As`, so generic status-based handling keeps working even for rate limits. `TypeSafeAPIConnectionError` and `TimeoutError` map onto `ConnectionError` and `TimeoutError` for the same reason — these represent failures that never reached an HTTP status at all, not variations on one. `TypeSafeAPIResponseValidationError.field_path` becomes `ResponseValidationError.FieldPath`, unchanged in purpose: both name the answer field that failed to decode. Field and predicate details live in [Errors and exit codes](../reference/errors-and-exit-codes.md); the shapes being decoded are in [Response types](../reference/response-types.md).

## Configuration that doesn't change at the edges

`TypeSafeClient(api_key=, base_url=, model=, retry=, timeout=, headers=, http_client=)` becomes functional options — `WithAPIKey`, `WithBaseURL`, `WithModel`, `WithRetryPolicy`, `WithTimeout`, `WithHeaders`, `WithHTTPClient` — passed to `NewClient`. `RetryPolicy` carries the same semantics as Python's `RetryPolicy(max_retries, backoff_max, timeout, ...)` under Go-idiomatic field names, not a redesigned retry model. The environment variables go further than "same semantics": `TYPESAFE_API_KEY`, `TYPESAFE_BASE_URL`, `TYPESAFE_DEFAULT_MODEL`, and `TYPESAFE_LOG_LEVEL` are identical names in both SDKs, so a deployment already exporting them for the Python SDK needs no changes to run the Go SDK alongside it or as its replacement. See [Client options and environment](../reference/client-options-and-environment.md) for the full resolution order.

Logging is a smaller, more mechanical difference. Python logs through the module-level `typesafe_sdk` logger, configured like any Python logger. Go has no ambient global logger to hook into, so it uses the standard `log/slog` package instead, configured either via `WithLogger` or by setting `TYPESAFE_LOG_LEVEL` to `debug`, `info`, `warning`, or `error`; anything else, `off` included, disables it (the default). What gets logged — method, path, status, duration, attempt, and request ID, with the `Authorization` header and bodies always excluded — is the same in both SDKs; only the mechanism for reaching that log line differs.

## What has no Python counterpart

The last row of the mapping is "none" on the Python side, covering three additions with a shared motivation: the `Instrumentation` hook, the `typesafe/otel` subpackage, and the `jev` CLI. None exist in the Python SDK because none are needed there — a Python caller can already generate and execute Python to drive Jev directly. The Go SDK exists partly to serve callers that can't or shouldn't do that: the future TypeSafe Claude Code plugin and other non-Go tooling need a way to call Jev — ask a question, get a typed judgment back — without shelling out to a Python interpreter. `jev` is that entry point as a standalone binary; `Instrumentation` and `typesafe/otel` exist so calls made that way can still be traced. They extend the surface rather than translate anything Python already had.
